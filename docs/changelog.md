# Changelog

All notable changes to BetterStatusPage are documented in this file.
The project follows [Semantic Versioning](https://semver.org/); while it is below 1.0, a new minor version marks new features.

## [Unreleased]

### Added

- **Performance benchmark**: `npm run bench` measures the scheduler, the write path and the public API against a temporary database with any number of monitors and days of history. Results for 10, 25, 100 and 250 monitors are in [Performance](performance.md).

### Changed

- **Credentials typed into a monitor, action or channel are encrypted**: database and HTTP monitor passwords, credential headers, webhook URLs, bot tokens and the SMTP password were stored in the clear (only vault secrets were encrypted), so a copy of the database or a backup carried them. They are now encrypted with `VAULT_ENCRYPTION_KEY` when written and decrypted when read; the first start after the upgrade encrypts the existing ones and needs the key set outside development. See [Vault](vault.md#credentials-typed-into-a-monitor-action-or-channel).
- **Account and token changes ask for your password**: creating a user, changing a role, resetting another user's password and creating an API token now ask you to confirm who you are (your current password, or single sign-on again), like resetting 2FA already did, and accept 5 attempts per 15 minutes. A stolen session alone can no longer add an administrator or create a token. API clients that call these endpoints with a session send `currentPassword` in the request body.
- **Revealing a secret and downloading a backup are in the audit log**: both are recorded as **Allowed** entries with the administrator's email (never the secret value), so a copy of a credential or of the whole database leaves a trace.
- **Faster checks with slow monitors**: scheduled checks share one limit of `MONITOR_CHECK_CONCURRENCY` slots, counted across all ticks and served in the order monitors became due, instead of chunks that each waited for their slowest check (and a limit that applied to each tick separately), so a few hanging monitors no longer delay the rest (a tick of 100 monitors with 10% hanging: 15 s before, 3.3 s now).
- **Cheaper Prometheus scrapes**: `/admin/metrics` reads the latest response time of each monitor with one index lookup per monitor instead of scanning every stored result, so a scrape no longer slows down as history grows.
- **No more blank screen on errors**: the admin and the public status page show a message with a **Reload** button when a page fails to render or a lazily loaded part cannot be fetched (typically after an upgrade replaced the files of an open tab), and the admin shows a spinner while a page loads.
- **Daily uptime totals**: the database keeps the checks of each monitor counted per UTC day, so the 90-day uptime on the status page, the uptime report, the static fallback and the daily bars of the monitor statistics are read from a few rows instead of counted from every result. At 100 monitors and 13 M results, the uptime of one monitor takes 0.3 ms instead of 65 ms and a cold view of the status page 38 ms instead of 6.4 s. Triggers on the results table keep the totals right, including retention, deleted monitors and failures confirmed later, and the benchmark checks them against the results. Recording a check takes about 0.1 to 0.2 ms longer. The first start after the upgrade counts the existing results once (about 5 s per 13 M results). See [Performance](performance.md#daily-totals).
- **Retention does not stop the server**: results older than `MONITOR_RESULT_RETENTION_DAYS` are deleted in batches of 5,000 per monitor, with the server free between the batches, instead of in one statement that held everything up for as long as it ran (0.6 s at 100 monitors and 2.2 s at 250). At 100 monitors the deletion takes 0.24 s in total and nothing waits longer than 23 ms.
- **Faster monitor statistics**: the response time percentiles (p50, p95, p99) are taken from the response times already loaded for the charts instead of three more queries over the window. The 30-day view of a monitor takes 71 ms instead of 119 ms at 100 monitors and 13 M results, the 7-day view 18 ms instead of 27 ms. The values are unchanged.
- **Response time charts of the status page are kept for 10 seconds**: visitors who ask for the same chart within 10 seconds share one query instead of running one each, which matters for long ranges (a 7-day chart takes 11 ms to count at 100 monitors and 13 M results, a 90-day one 183 ms) and when an incident brings many visitors at once.

### Fixed

- **Status page works when the browser blocks storage**: a browser that denies access to local storage (strict privacy settings, some embedded views) left the public status page and the admin blank. Theme, language and similar preferences are now simply not remembered in that case.
- **Single sign-on secret after changing the issuer**: changing the issuer URL or client ID in the SSO settings now requires entering the client secret again, so the stored secret is never sent to a different identity provider.
- **Confirming an outage no longer scans the whole history**: marking the checks of a failing streak as counted looks them up by time on the monitor's index instead of walking its whole history, so a mass outage no longer holds the database for seconds (36 ms to 0.03 ms for a monitor with 130,000 results).
- **Check errors are no longer swallowed**: a monitor whose stored configuration cannot be read is recorded as **Down** with the error, instead of the check aborting without a result and the monitor staying at its last status (for example **Up**). A failure to store a check result is logged with the monitor ID.
- **Alternating down and degraded now alerts**: with a failure threshold above 1, a monitor that swapped between **Down** and **Degraded** on every check never reached the threshold, so it never alerted and its results counted as healthy. Both statuses now form one failing streak and the alert reports the last one. Monitors that behaved like this will start alerting.
- **Secret headers stay with the monitored origin**: a redirect to another origin carries only `Accept*`, `User-Agent` and `Cache-Control` from the configured headers (fetch removed only `Authorization` and `Cookie`, so `X-Api-Key` followed an open redirect) and no request body; the upgrade of an `http://` URL to `https://` on the same host keeps them. CAS session cookies go only to the host that set them (and the subdomains of its `Domain`), `Secure` ones only over HTTPS. The OAuth2 token request is not redirected, so the client secret is never sent again to the address of a `307`/`308`. Switching on **Ignore TLS certificate errors** requires entering stored secrets again; switching it off does not. See [Monitors](monitors.md).
- **TLS mode for database monitors**: SQL Server, PostgreSQL, MySQL / MariaDB and MongoDB monitors in individual-fields mode have a **Connection security** setting (`tls`: `verify`, `require` or `prefer`) and an optional CA certificate (`tlsCa`). `verify` checks the certificate and host name, `require` encrypts without a plain-text fallback, and `prefer` keeps the earlier behaviour (PostgreSQL and MySQL fell back to plain text when the server answered that it had no TLS, which let a party on the network path read the password; MongoDB was not encrypted). The form starts new monitors at `verify`; existing ones, and monitors from the API or configuration files without `tls`, stay at `prefer` until changed, and the form warns about it. The documentation recommends read-only accounts, since a monitor runs the query as written. See [Connection security](monitors.md#connection-security).

- **Response bodies are read up to 1 MB**: the keyword check, JSON assertions, the test runner and the token and ticket requests of authentication read a response through one limited stream and cancel it after 1 MB, so a target that streams without end (chunked, no `Content-Length`) can no longer exhaust the memory of the server, including through the test button. The keyword is searched in the first 1 MB, a larger body fails JSON assertions as before, and the test reports its size as `more than 1 MB`.
- **Monitors cannot read cloud metadata services**: HTTPS monitors, the test runner, the certificate reading and HTTP actions and Docker monitors on a TCP endpoint refuse to connect to link-local and cloud metadata addresses (`169.254.0.0/16`, `fe80::/10`, `fd00:ec2::254`, `fd20:ce::254`, `100.100.100.200`, `metadata.google.internal`), checked on the address actually connected to, so redirects and DNS rebinding do not get around it. Private networks stay reachable; `MONITOR_ALLOW_METADATA=true` lifts the block. A failed response check quotes the answered value only for administrators in the test runner; scheduled checks (stored and sent in notifications) and operators see `the value is not shown`. Results already stored are unchanged. See [Where a monitor may connect](monitors.md#where-a-monitor-may-connect).
- **Manage links are not readable from a copy of the database**: the token behind the manage and unsubscribe links is stored encrypted (like webhook headers) and looked up by its SHA-256 instead of lying in the `subscribers` table in the clear, so a database copy or a backup alone no longer allows changing or cancelling every subscription. Existing tokens are encrypted on the first start after the upgrade and links already sent keep working. The upgrade needs `VAULT_ENCRYPTION_KEY` set to the key of the installation (it refuses to run without it) and cannot be rolled back without restoring a backup, because an older version would put the encrypted value into the links. Notifications need the key to build the link, as they already do for webhook headers; if the key is lost they are retried and no webhook subscriber is paused because of it.
- **Subscription form cannot be used to flood a mailbox**: the 10-minute cooldown on confirmation emails is kept per email address instead of per destination, so submitting the same address with ever new webhook URLs no longer sends a mail each time, and an address can have at most 5 unconfirmed, unexpired subscriptions. The public rate limits count an IPv6 client per /64 instead of per address, since one client is routinely given a whole /64.

- **Live streams cannot exhaust the server**: the live event streams (`/events` of the status page and of the admin) are limited to 10 open anonymous streams per address (an IPv6 /64 counts as one address) and 1,000 in total (`SSE_MAX_CLIENTS_PER_IP`, `SSE_MAX_CLIENTS`; further streams get `429`; signed-in streams are not counted, so visitors cannot lock out the admin), a stream whose client stops reading is closed once more than 1 MiB is waiting to be sent, and opening the public stream is rate-limited to 30 times per minute per address. The status page retries a failed stream with a growing delay (2 s up to 1 min) instead of every 2 s, and refreshes its data every 30 s while the stream is down, showing the refreshed statuses rather than ones received before the stream dropped. The admin monitor list backs off the same way. Before, many streams that never read could fill the memory or the file descriptors of the server.

- **Response time history answers only what the page's charts ask for**: `GET /api/v1/public/monitor/:id/history` answers `404` unless a chart block in the published layout shows that monitor with exactly that `hours` and `buckets`. Before, any of about 196,000 combinations per monitor was computed on request, and a 90-day one blocks the server for about 180 ms, so an anonymous client within the rate limit could keep the server busy for most of every minute and fill the 10-second cache with entries of its own. Monitors shown only as a status card have no history endpoint; the status page does not request one.
- **Setup cannot take over an existing instance**: if `setup.json` is lost (a data directory outside the volume, a recreated container) or cannot be read while the database remains, the setup wizard no longer creates an administrator or overwrites the password of an existing one. Setup is refused (409) when the database already has any user, and an unreadable `setup.json` counts as setup completed. In such a case restore `setup.json`, or recreate it as `{"setupComplete": true, "dbType": "sqlite"}`.
- **Feed and status API links cannot be poisoned in a shared cache**: without `PUBLIC_URL`, the RSS/Atom feeds and `summary.json`/`components.json` build their links from the request host (behind `TRUST_PROXY`, from `X-Forwarded-Host`) and are cacheable by CDNs. They now send `Vary: Host, X-Forwarded-Host, X-Forwarded-Proto`, so a request with a forged host cannot make a cache serve links to another domain to everyone. Setting `PUBLIC_URL` avoids the dependence on request headers altogether.
- **Public incidents do not name internal monitors**: the `autoMonitorId` of an incident opened by a monitor that is not in the published layout is `null` in the incident lists, details, status data and live events of the status page, like the links in `monitorIds`.
- **Setup validates its input**: an email or password that is not a string gets a 400 instead of an error.
- **Checks and heartbeats no longer overwrite each other**: a check's result is now judged against the monitor's state at the moment it is recorded, not against the row read before the check started, so a heartbeat that arrives while a check is queued or running keeps its failure count. A monitor that was deleted or already observed while it waited for its turn is skipped, and the result and the monitor's state are saved in one transaction (about 30% faster per check).
- **No duplicate check after "Check now"**: the end of a scheduler tick no longer releases a monitor that "Check now" has just started, which could let the next tick check it a second time and repeat an alert.
- **Transactions no longer collide**: database transactions that start at the same time now take turns instead of failing with "cannot start a transaction within a transaction". With the single connection, several checks finishing together (for instance heartbeat monitors that all missed their interval) could lose all but one of their results, and a heartbeat arriving at that moment could get an error.

## [0.6.0] - 2026-10-20

### Added

- **Static fallback**: the instance pushes a saved copy of the public status page (the page, its files and a `snapshot.json` with statuses, layout, incidents, 90 days of uptime and translations) to S3-compatible storage (AWS S3, Cloudflare R2, Backblaze B2, MinIO) every minute or at an interval you choose, so visitors still see the last known state, with a banner saying when it was taken (optional), when the server is down. Set it up in **Static fallback** (administrators only): pick a provider for hints on where to find the endpoint and key, **Check access** tries the key without pushing, and **Save and turn on** starts the first push. The page shows the state in words, what the copy holds and one bar per recent push; **Push now** pushes once on demand while the mirror is on, and **System Health** has a **Static fallback** card. The secret key is stored encrypted, the snapshot holds only what the public page serves, and a private page is never pushed. The admin API serves it at `/admin/static-mirror`. See [Static fallback](static-fallback.md).
- **Recurring maintenance windows**: a maintenance window can repeat every day or on chosen weekdays (**Repeat**, optionally **Repeat until**), so nightly builds and weekly release or backup windows are entered once. The time of day is read in the timezone the window was created in, and alerts stay silent during every occurrence. **End now** ends only the running occurrence (`POST /maintenance/:id/end`). The API takes `recurrence`, `recurrenceDays`, `timezone` and `recurrenceUntil`, and returns `occurrence`. See [Recurring windows](incidents-and-maintenance.md#recurring-windows).
- **Maintenance and incidents on monitors**: the Monitors list, the Dashboard and a monitor's page show a **Maintenance** chip while a window covers the monitor, and **Incident · impact** while an open, published incident names it, coloured by impact. The monitor list and `GET /monitors/:id` in the API carry `activity` (`maintenance`, `incident` and `windows`, the running and upcoming windows covering the monitor). A monitor's page has a **Maintenance** card with those windows, and a token without the `maintenance` permission gets `windows` empty. See [What happens during a window](incidents-and-maintenance.md#what-happens-during-a-window).
- **Maintenance does not lower uptime**: a failed check inside a maintenance window is left out of the uptime on the status page, in the monitor statistics and in the uptime report. Checks keep running and are recorded, and the failure list in the monitor details marks them as *maintenance*. Results recorded earlier are unchanged. A day with nothing but such failed checks shows as **Maintenance** (blue) on the uptime bar instead of *No data* (`GET /public/monitor/:id/uptime` returns the day with `status: "maintenance"` and a `maintenanceChecks` count, and the response time chart draws no outage band for such a stretch, its tooltip says Maintenance), and the tooltip of a day that has some says that maintenance is not counted. See [What happens during a window](incidents-and-maintenance.md#what-happens-during-a-window).
- **Native arm64 image**: the published image is now a multi-platform manifest (`linux/amd64` and `linux/arm64`), so `docker pull` works on arm64 hosts such as Raspberry Pi and Apple Silicon servers without changing the tag.

## [0.5.0] - 2026-10-18

### Added

- **Webhook monitor reports down and degraded**: a heartbeat URL accepts `?status=up|down|degraded` and `?msg=<reason>` (up to 500 characters), so a job that failed is detected at once and with a reason. Without parameters the call records `up` as before. The same alert thresholds and maintenance windows apply. See [Reporting a failure](monitors.md#reporting-a-failure).
- **Ignore TLS certificate errors**: an HTTPS monitor can accept self-signed, expired or mismatched certificates, so devices on a LAN keep status code, keyword and response checks. Off by default; set in the monitor form, or as `ignoreTls` in the monitor's `config` in the API and configuration files. It disables certificate verification for the monitored host and port, a redirect to another host or port is still verified (in the check and in the **Test** button), and certificate expiry warnings do not apply to such a monitor. See [Ignore TLS certificate errors](monitors.md#ignore-tls-certificate-errors).
- **Optional prune on configuration import**: `POST /config/validate` and `/config/apply` accept `?prune=true`, and the Import page has a **Delete what the file does not mention** switch, so a file in a repository can be the single source of truth. Monitors, notification channels and actions that the documents do not mention are deleted, with their links, but only for the kinds the file holds, so a file with only monitors leaves channels and actions alone. **Export YAML** on **Monitors** and **Notifications** shows the whole configuration as one file, so there is something to start a file from. The preview and `validate` list every deletion first (`"action": "delete"`) and the page asks for confirmation before it applies them, the YAML on the Import page and in the YAML dialogs is coloured (keys, strings, numbers and booleans, comments), and the Import box can be resized by its bottom-right corner. A link in the file to something the same import deletes (a monitor that lists a channel, action or monitor which the file leaves out) is refused with a problem naming it, instead of being dropped without a word. The deletions are audited, and without the option nothing is deleted, as before. See [Removing what the file leaves out](configuration-as-code.md#removing-what-the-file-leaves-out).
- **Resizable and sortable table columns**: the lists of users, API tokens, monitors, notification channels, actions and the uptime report can be sorted by clicking a column title (click again to reverse, a third time to switch the sorting off; empty values stay last). Every admin table, including the audit log, has columns that can be resized: drag the line on the right edge of a column title, or focus it and use the left and right arrow keys; the column next to it takes or gives the space, so the other columns stay put. Double-click or Home restores the default layout. Sorting and widths are kept until the page is reloaded.
- **Heartbeat token in configuration files**: a `webhook` monitor document can carry `heartbeatToken`, so a monitor that is created again keeps the URL its senders call. The export writes the mask instead of the value, and an import without it keeps the stored token. See [Heartbeat token](configuration-as-code.md#heartbeat-token).

### Changed

- **Placeholder in the user or password of an action URL**: saving an action whose URL has a placeholder before the `@` (`https://{{secret_x}}@host/`) is now refused, because the request cannot carry credentials in the URL. Send them in the `Authorization` header, for example with `{{secret_x_basic}}`. See [Actions](actions.md).
- **Variables in a webhook channel**: in the URL of a webhook channel each `{{variable}}` is now URL-encoded (a value of only dots is sent as the text `%2E`), so a monitor name with spaces or `&` stays one query value, and line breaks are removed from header values. A URL that relied on a raw value, for example a variable that holds a path with `/`, now gets it encoded. See [Notification channels](notification-channels.md).
- **Placeholder in the host of a URL**: a `{{variable}}` in the scheme, host or port of the URL of an action or of a webhook channel (`https://{{error_message}}/x`) is now refused when it is saved, and the request is not sent for one saved earlier, because a value filled in when it runs (the `msg` of a heartbeat, a monitor name) would choose where the request goes. Put variables in the path, the query or the body. See [Actions](actions.md) and [Notification channels](notification-channels.md).
- **Markup in alert text**: the error text of an alert (for example the `msg` of a heartbeat) could carry Slack mentions and links (`<!channel>`, `<https://…|text>`), Discord and Teams links, or a Discord `@everyone` ping. It is now shown as plain text. The error field of Slack, Discord and Teams alerts is escaped, and so are the variables in the Slack message text and `{{error_message}}` in the Discord message content (a variable in the Discord avatar URL is URL-encoded). Text you write into the template itself is unchanged. See [Slack](slack-integration.md#message-text-and-template-variables) and [Discord](discord-integration.md#message-content-and-template-variables).
- **Heartbeat in the logs**: the heartbeat token in the path (`/api/v1/hook/<token>`) and the `msg` of a heartbeat are replaced by `[redacted]` in the request log, like the unsubscribe `token`. Names of query parameters are matched after decoding.

### Fixed

- **BetterStatusPage link on the status page**: the small link in the bottom-right corner opened the GitHub repository. It now opens <https://betterstatuspage.dev>.
- **Large image assets**: `icon.png`, `logo_light.png` and `logo_dark.png` of the admin and the status page were about 2 MB each. They are now scaled to the size they are shown at (about 70 KB for the icon and 370 KB for each logo) with their transparency kept.
- **Status page before the setup**: opening the address of a new instance without `/admin` logged `Error: DB not initialized` and showed a broken page. It now redirects to the setup wizard until the first administrator is created.
- **ICMP ping monitors in a container**: when the host did not allow unprivileged ICMP, or the `ping` command was missing, the monitor reported a bare system message that looked like a dead target. It now says that ICMP is not permitted (or that `ping` cannot be run) and how to fix it. `docker-compose.yml` has a commented `sysctls` example and the Ping / TCP and deployment docs explain the setting.
- **`npm run db:migrate` and `npm run db:seed`**: did not work. `db:migrate` did nothing and `db:seed` failed with "DB not initialized". `db:migrate` now opens the database and applies the migrations; `db:seed` also applies them, creates the administrator and the default branding and layout, and marks the setup as done so the server skips the setup wizard. Both can be run again safely.
- **Faster `npm run dev`**: the shared packages are rebuilt only when they changed, so a start with no changes no longer spends about 12 seconds building ten packages.

## [0.4.0] - 2026-10-14

### Added

- **ntfy and Pushover notification channels**: send monitor alerts, recoveries and TLS certificate warnings as push notifications to a topic on ntfy.sh or your own ntfy server, or to a Pushover user or group. A down monitor is sent with high priority. The ntfy access token and the Pushover application token are shown only by their last four characters once saved, and can be read from the vault. The API and configuration files gain the `ntfy` (`topic`, `serverUrl`, `accessToken`) and `pushover` (`appToken`, `userKey`) channel types. See [ntfy and Pushover](notification-channels.md#ntfy-and-pushover).
- **HTTPS response checks and slow-response limit**: an HTTPS monitor can check the headers of the final response (exists, does not exist, equals, does not equal, contains) and fields of a JSON body by path such as `$.queue.length` (exists, equals, does not equal, contains, less than, greater than), each failing as **Degraded** or **Down**, and **Degraded when slower than** turns a slow response Degraded. Set in the **Checks** side tab of the monitor form; the **Test** button lists every check. The API and configuration files gain `assertions` and `degradedAboveMs` in an HTTPS monitor's `config`. A JSON body over 1 MB is not parsed. See [Response checks](monitors.md#response-checks).
- **Actions**: an action sends an HTTP request when a monitor stays down or comes back up, for example to start a failover job in Jenkins. **Alerts → Actions** (administrators) creates actions with a URL, method, headers and a JSON body that accept the same `{{variables}}` as a webhook channel; the **Actions** side tab of a monitor links them to a status with a delay in minutes (a `down` action is dropped if the monitor recovers first) and a cooldown. Runs are retried up to 3 times, survive a restart, and are listed in the run history in **Delivery history → Actions**, where a failed run can be retried by hand. **Run now** shows the HTTP status and the start of the answer. Tokens and passwords are kept in **vault secrets**, any number of them, each under a name and used as `{{secret_<name>}}` (or `{{secret_<name>_basic}}` for a user and password) in the URL, headers or body, so they are never stored with the action or shown in the history; the **Secrets** and **Notify when a run fails** tabs sit at the right edge of the form. Redirects are not followed. The channels chosen under **Notify when a run fails** are told once a run has failed after its last attempt (a new **Action failed** event). Actions are exported and imported as `Action` documents, and a monitor lists them in `actions`. The API gains `/actions` and a new `actions` token permission, and `GET /config/export` leaves actions out for a caller who may not read them. See [Actions](actions.md).

## [0.3.0] - 2026-10-11

### Added

- **Longer chart ranges and uptime % in the chart block**: the status page chart block can show the last 30 or 90 days, and **Show uptime %** adds the monitor's uptime over the same range to its header. `GET /api/v1/public/monitor/:id/history` accepts `hours` up to 2160 (was 168). See [Customizing the status page](customizing-the-status-page.md).

- **Prometheus metrics**: `GET /api/v1/admin/metrics` exposes monitor status, latest response time, last check time, TLS certificate expiry and the number of open incidents in the Prometheus text format. It is protected by an API token with the new read-only `metrics` permission. See [Prometheus metrics](api.md#prometheus-metrics).

- **Automatic incidents**: a monitor can open an incident by itself when it stays down for a set number of minutes (set in the **Incident** side tab of the monitor's form) and resolve it after recovery. The incident is created as a **draft**, visible only in the admin console until you press **Publish**, or published right away. **Incidents → New Incident** can also save a draft. Incidents are written from **incident templates** with `{{monitor}}`, `{{duration}}`, `{{error}}` and `{{status}}` placeholders: a built-in default one, which can be edited, and custom ones (**Incidents → Templates**), chosen per monitor. The API gains `autoIncidentMinutes`, `autoIncidentMode` and `autoIncidentTemplateId` on monitors, `draft` on incidents and `/incident-templates`. Templates can carry wording for each language of the status page, so a visitor who switches language sees the automatic incident in it. Configuration files can switch them on with an `autoIncident` block (see [Configuration as code](configuration-as-code.md#automatic-incidents)). See [Automatic incidents](incidents-and-maintenance.md#automatic-incidents). Downgrading to a build without drafts would show draft incidents publicly.

- **New-version notice**: the **Application** card on **System Health** links to the release when GitHub has a newer one. The server checks in the background every 6 hours and shows the result on the Dashboard to administrators too; `UPDATE_CHECK=false` turns the check off. See [System Health](users-and-roles.md#system-health).

- **What's new and documentation link**: after an update each user sees **What's new** with the entries of the changelog they have not seen, and the sidebar has a **Documentation** link. See [Documentation link and What's new](users-and-roles.md#documentation-link-and-whats-new). The Dashboard of an instance without monitors has an **Add your first monitor** button.

- **Install script**: `curl -fsSL https://betterstatuspage.dev/install.sh | sh` downloads the Compose file and `.env` template, generates `JWT_SECRET` and `VAULT_ENCRYPTION_KEY`, and starts the container. It is safe to run again and never overwrites an existing `.env`; `BSP_DIR` and `BSP_REF` change the install directory and the downloaded branch or tag. See [Quick install](deployment.md#quick-install-script).
- **Telegram notification channel**: send monitor alerts, recoveries and TLS certificate warnings to a Telegram chat, group or channel through your own bot (bot token and chat ID), with the same severity emoji, optional templated line and alert hygiene as the other channels. A saved bot token is shown only by its last four characters, and it can be read from the vault instead of being stored in the channel. See [Telegram integration](telegram-integration.md).
- **HashiCorp Vault**: a vault can now read its secrets from a HashiCorp Vault KV v2 engine, using a token or AppRole, with an optional namespace and CA certificate. Secrets are references to a path (and key); values are read live on every use and never stored. Monitors and SMTP settings pick them from the same **From Vault** switch. **Test connection** checks the credentials, also before the vault is saved. The token, or the Role ID and Secret ID, can be read from a secret in a local vault instead of being typed (a Secure Value, User / Password or JSON secret). See [HashiCorp Vault](vault.md#hashicorp-vault). Downgrading to a version without this support leaves these vaults unusable until you upgrade again.

- **Monitor details page**: click a monitor's name in **Monitoring → Monitors**, or its tile on the **Dashboard**, to see its response time chart (average, p95 or maximum, in the style of the status page), uptime bars (hourly, 6-hourly or daily, depending on the range), response percentiles (p50, p95, p99), the 10 latest failed checks with their errors, incidents with their MTTR and the monitor's configuration, for the last 24 hours, 7, 30 or 90 days. See [Monitor details](monitors.md#monitor-details).

- **Keys for monitors and notification channels**: every monitor and notification channel now has a unique, technical **key** (lowercase letters, digits, `-` and `_`) next to its name. The admin panel does not show it in its forms. It is generated from the name, or given when the object is created through the API, and never changes afterwards, not even when the name does; it identifies the object in API clients and configuration files. Existing monitors and channels get a key from their name when the database is upgraded (`name`, then `name-2`, `name-3` for repeats); downgrading to a build without keys is not supported once the keys exist.

- **API tokens**: **Administration → API tokens** creates tokens for scripts and CI/CD. A token carries the permissions you tick, per part of the application, instead of a role: read or write for monitors, notification channels, incidents, maintenance windows, subscribers and the status page's appearance, read for reports, the audit log and system health, and a separate `vault:use` permission to use vault secrets in monitors, channels and the SMTP settings (write includes read). The presets **Report incidents**, **Deploy monitoring** and **Read only** fill in the usual sets. A token expires after 90 days unless **Never expires** is chosen, is sent as `Authorization: Bearer <token>` to the admin API, and is shown once; only its hash is stored. A request without the needed permission is refused with `403` naming it. A token cannot manage users, single sign-on, status page access, vaults, backups or other tokens, belongs to no user (it keeps working when the administrator who created it is demoted or deleted), is limited to 300 requests per minute, and is named in the audit log as `token: <name>`. See [API](api.md#permissions).

- **OpenAPI description of the admin API**: [`openapi.yaml`](https://docs.betterstatuspage.dev/openapi.yaml) documents the operations meant for scripts and CI/CD (monitors, incidents, maintenance windows, notification channels, layout, configuration export and import) with their bodies, limits and the permission each needs. See [API](api.md).

- **Configuration as code**: monitors and notification channels can be written as YAML documents with a `kind` (`Monitor`, `NotificationChannel`), identified by key instead of numeric id, with known secret fields masked as `••••••••` and vault secrets named by vault and secret. Several documents can share a file, separated by `---`. See [Configuration as code](configuration-as-code.md).
  - **YAML button**: a monitor (its page and its edit form), and a notification channel (its edit form) have a **YAML** button that shows the saved object as a document, with **Copy** and **Download**. It is read only.
  - **Import**: the **Import YAML** button on **Monitors** and **Notifications** takes pasted or uploaded documents (up to 2 MB), checks them as you type, lists what they would create and update (never the values of settings), or every problem with its place, and applies them completely or not at all. Importing needs the Operator role. An import never deletes anything, and a stored secret is kept when the document has `••••••••` in its place.
  - **API**: `GET /api/v1/admin/config/export` writes every document, or one with `?kind=&key=`; `POST /config/validate` and `/apply` read YAML only: one document or several separated by `---`. A token needs `monitors` and `channels` permission for the kinds involved, and `vault:use` to add a vault reference or change a monitor or channel that has one. Changing which channels a monitor alerts through also needs `channels:write`.

### Changed

- **Database credentials moved to a side tab**: for a Database monitor, the user and password (or the Vault secret holding the connection string) are now on a **Credentials** tab beside the form, like **Auth** for an HTTP(S) monitor. It opens by itself when you choose the Database type, shows ✓ when credentials are set and ! when they are missing, and a database monitor can no longer be saved without them. See [Database monitors](monitors.md).

- **Admin menu regrouped**: the sidebar now has **Monitoring**, **Alerts** (**Notifications** and **Delivery history**), **Status page** (**Page Builder**, **Branding**, **Localization**, **Subscribers**) and **Administration**. Import has no menu entry any more: **Monitors** and **Notifications** have an **Import YAML** button instead.

- **Saved secrets are masked everywhere**: a monitor's password, OAuth2 client secret, database password and credential headers, and a channel's Slack, Discord or Teams webhook URL, webhook credential headers and Telegram bot token now read back as `••••••••` in the form and in the API. Leave a field untouched to keep the stored value, or enter a new one. The **Test** button of a saved monitor uses the stored secrets. A stored secret is only kept while it is sent to the same place: changing a monitor's URL, token URL, CAS server, database host or port, or a webhook channel's URL asks you to enter the secrets again. See [Saved secrets](monitors.md#saved-secrets).
- **Stricter input checks in the API**: a monitor's `intervalSecs` (10 to 86400), `timeoutMs` (1000 to 300000), `retries` (1 to 10), `config` (an object) and `tags` are validated, a maintenance window needs a name and a start before its end, with existing monitors, a channel's `config` must be an object, `PUT /layout` needs a `tree`, and changing the type of a monitor or channel needs a new `config` in the same request. The admin panel already stayed within these limits.
- **Notification channel type picker**: the type in **New Notification Channel** is now a searchable dropdown, like the monitor type, instead of a row of buttons, so it stays one control tall as more channel types are added.

### Fixed

- **Switching a monitor to credentials from a vault**: choosing **From Vault** for a monitor's basic, OAuth2, CAS or database credentials now removes the username, password or client secret that were entered directly, so a monitor no longer keeps both (and shows both in its YAML).
- **Development restart after a killed process**: starting the API no longer fails with "BetterStatusPage is still running" when the previous process was killed (Ctrl+C or a hot reload on Windows) less than 30 seconds earlier.
- **Date and time format**: the admin panel shows dates as `dd.mm.yyyy` and 24-hour time by default, regardless of the browser language. **Settings → Date and time format** lets you pick `dd-mm-yyyy`, `mm/dd/yyyy`, `yyyy-mm-dd`, `yyyy.mm.dd` or 12-hour time; the choice is stored per browser. See [Date and time format](users-and-roles.md#date-and-time-format).

## [0.2.1] - 2026-10-08

### Added

- **PostgreSQL, MySQL / MariaDB and MongoDB monitors**: run a test query (for MongoDB, a JSON command), like the SQL Server monitor. They appear in the form as one **Database** type with an **Engine** selector, together with SQL Server. Connect with individual fields or a connection string from the vault; an optional **Expected Result** (first column of the first row) makes a mismatch Degraded; includes the **Test** button. MySQL and MariaDB share one type. See the [monitors guide](monitors.md#sql-server-postgresql-mysql--mariadb-and-mongodb).
- **Docker monitor**: checks the state and healthcheck of a container through the Docker Engine API, over a local socket, a Windows named pipe or HTTP(S). Running and healthy is operational; restarting, unhealthy or starting is degraded; stopped, paused or missing is down. Includes the **Test** button. See the [monitors guide](monitors.md#docker).
- **Subscriber delivery history**: the **Subscribers** tab of **Monitoring → Delivery history** lists every notification sent to subscribers with its status, attempts and last error, filters by status, event and subscriber (the history icon on a subscriber's row), and has **Retry now** for failed deliveries. See [Delivery history](subscriptions.md#delivery-history).

- **Uptime reports**: **Monitoring → Reports** shows the uptime, checks, average response time and incident count of every monitor for any date range (up to 366 days, within the result retention), and exports it as a summary or daily CSV. See [Uptime reports](reports.md).

- **Status page link in the admin sidebar**: **Status page**, above **Settings**, opens the public status page in a new tab.

### Changed

- **Delivery history moved to Monitoring**: the notification and subscriber delivery histories are now the two tabs of one **Monitoring → Delivery history** page, instead of separate pages under Notifications and Subscribers. The **Delivery history** buttons on those pages and the history icon on a subscriber's row open the right tab, and the old addresses redirect. See [notification delivery history](notification-channels.md#delivery-history) and [subscriber delivery history](subscriptions.md#delivery-history).
- **Faster loading**: the admin panel loads each page on demand, and the public status page loads its charts only when the page has one, so the first load transfers noticeably less JavaScript.
- **Subscribers page**: now two tabs, **Subscribers** and **Settings**. Methods are listed as rows with **Copy** buttons for their addresses, and a bar at the bottom offers **Save settings** and **Discard** while there are unsaved changes. In the list, tick subscribers to **Export** them as CSV or **Delete** several at once; **Export CSV** exports the current filter. See [Managing subscribers](subscriptions.md#managing-subscribers).
- **Monitor form**: the type is picked from a searchable list grouped by area instead of a row of buttons, so the form no longer grows with every new monitor type. The type-specific fields now come right after the type, and **Interval**, **Timeout**, **Attempts**, **Alert after** and **Recover after** sit in a collapsed **Schedule & alerting** row that shows their current values.

### Fixed

- **Incidents block**: an **Incident limit** above 10 now works on the public status page. It fetched at most 10 resolved incidents, whatever the limit was.
- **Discord notifications**: the channel form now has an **Avatar URL** field, so saving a channel no longer drops an avatar set through the API. Without an avatar, messages use the BetterStatusPage logo.
- **Audit log**: the **Entity** filter now lists every recorded type: user security, branding, page layout, languages, backups, backup schedule and notification deliveries.
- **Delivery history**: the **Event** filter now includes **Certificate**.
- **HTTP(S) monitor**: a GET or HEAD monitor with an empty request body now passes scheduled checks, not only the **Test** button. The body is ignored for these methods.
- **Ping monitor**: the **Test** button now sends an ICMP ping in ICMP mode, instead of always opening a TCP connection.
- **Webhook notifications**: variables such as `{{error_message}}` are now escaped inside the JSON body, so quotes and new lines no longer produce invalid JSON.
- **SMTP with a Vault secret**: a **Secure Value** secret (no username) now makes sending fail with a clear error instead of silently sending without signing in. The SMTP form warns about it.
- **Maintenance windows**: saving a window with no monitors selected and "all monitors" unchecked is now rejected with a message, instead of being saved as a window that suppresses nothing.
- **Status page translations**: English text overrides set in **Settings → Translations** now apply on the public status page.

### Removed

- **"None" incident impact**: the option is gone from the incident form, along with its translation key `incident.impact.none`. Incidents now have `minor`, `major` or `critical` impact.

## [0.2.0] - 2026-10-02

BetterStatusPage now has a home of its own: the project website at [betterstatuspage.dev](https://betterstatuspage.dev) and full documentation at [docs.betterstatuspage.dev](https://docs.betterstatuspage.dev).

### Added

- **Single sign-on with OpenID Connect**: Microsoft Entra ID, Keycloak, Okta, Google Workspace, Authentik, Auth0 and other providers, configured in **Users → Single sign-on** without a restart. Authorization Code flow with PKCE, `state` and `nonce`. See the [single sign-on guide](single-sign-on.md).
  - The first sign-in matches the account by verified email, then links it to the provider's issuer and `sub`, so later sign-ins keep working when the email changes.
  - Microsoft Entra ID verified-email claim (`xms_edov`) is supported.
  - Password sign-in can be disabled while SSO is active, with safeguards against locking everyone out.
  - Two-factor authentication still applies after an SSO sign-in for users who turned it on.
  - Every sign-in, allowed or denied, is written to the audit log with the reason.
- **Private status pages**: the page shows its content only to signed-in users; everyone else gets a sign-in screen in the page's own branding. See the [private status page guide](private-status-page.md).
- **Viewer role**: can view a private status page but not the admin console. SSO can create viewer accounts automatically for the email domains you list.
- **Documentation site** at [docs.betterstatuspage.dev](https://docs.betterstatuspage.dev).

### Changed

- Users are no longer asked to change their password when password sign-in is disabled.

### Fixed

- Page builder: dragging blocks into groups.

### Upgrading from 0.1.x

Point `BSP_IMAGE` in `.env` at the `0.2.0` image tag, then `docker compose pull && docker compose up -d`. Database migrations run automatically on startup and no new `.env` variables are required. SSO uses `PUBLIC_URL` to build its callback URL, so set it before turning SSO on.
